# Homelab plan — enterprise function on the hardware already here

Six weeks, no purchases, reinstalls allowed where they pay. Every item is a
deletion, a hardening step, or a gate. Nothing is bought and nothing is added
unless something larger comes out or a real gap closes.

Start date: 2026-09-07.

---

## What "enterprise" means here

Not more services. Five properties, and everything below is in service of one
of them:

1. **Nothing important depends on one machine.**
2. **A compromised host cannot destroy the backups.**
3. **The network is segmented and least-privilege by default.**
4. **Every change is a commit; every failure is an alert that arrives.**
5. **Recovery is a rehearsed procedure with numbers, not an intention.**

# Week 1 — Fewer moving parts

Day-by-day, because this is the week that starts tomorrow.

## Day 1 — Alerting stops going through n8n

n8n is the single funnel for Alertmanager, Flux and the `pve-2` hardware
checks. Nothing else in this plan can be done safely while the only
notification path is also a deletion candidate.

| Path today | Path after |
|---|---|
| Alertmanager → `n8n/webhook/alertmanager` → LLM triage → Telegram | Alertmanager `telegramConfigs` → Telegram |
| Flux `Provider` type `generic` → `n8n/webhook/flux` | Flux `Provider` type `telegram` |
| `pve-2` hardware webhook → n8n | `nightly-checks.sh` curls the Telegram API |
| daily news digest | deleted, not replaced |

Both speak Telegram natively. The exact shapes, so this is not a research task
at the keyboard:

- `AlertmanagerConfig` takes `telegramConfigs` with `botToken`, `chatID`,
  `sendResolved`.
- Flux's `Provider` takes `type: telegram` and **ignores `address` entirely**.
  The chat goes in `channel` — a negative id like `-1001234567890`, or
  `@username` — and the token in `secretRef`.

The bot token moves out of `n8n/app/secret.sops.yaml` into `alertmanager-secret`
and a `telegram-token` secret in `flux-system`.

What actually goes away is the LLM triage step: a local `qwen3:4b` on CPU sat
between an alert firing and the phone buzzing. It rewrote text. It could not add
information Alertmanager did not already have, and it added two processes that
can hang.

**Files:** `kubernetes/apps/observability/kube-prometheus-stack/app/alertmanagerconfig.yaml`
· `kubernetes/apps/flux-system/notifications/app/provider.yaml` ·
`proxmox/pve-2/scripts/nightly-checks.sh`

**Gate:** kill a pod → Telegram. Break a Kustomization on purpose → Telegram.
Fail a nightly check on purpose → Telegram. All three, before Day 2.

**Rollback:** revert the commit. n8n is still running.

## Day 3 — Garage S3 → NFS backupstore

Longhorn backs up to a Garage S3 LXC on `pve-2`, whose data already lives on
`media/backups/longhorn-garage/` and whose metadata is copied off an SSD nightly.
The export is already mounted by all three nodes. So S3 is a translation layer
on top of a path the cluster can already reach.

It is also a circular dependency in DR: restoring volumes needs Garage, Garage is
an LXC on `pve-2`, and `pve-2` is exactly the host whose loss makes you want the
volumes back.

| Delete | Add |
|---|---|
| LXC 103 `garage-r730xd` (2 vCPU, 2 GB) | `backupTarget: nfs://10.57.57.250:/media/backups/longhorn` |
| `garage_setup` role + playbook | — |
| `garage-meta-nightly-copy.sh` + its 03:01 cron line | — |
| `rpool/garage-meta` dataset | — |
| `minio-secret.sops.yaml` | — |

Longhorn's NFS backupstore requires **NFSv4** (4.0, 4.1 or 4.2) — confirm
`nfs-kernel-server` on `pve-2` is not restricted to v3 first. URL form is
`nfs://server:/export/path`. Default mount options are
`actimeo=1,soft,timeo=300,retry=2`, and anything passed via `?nfsOptions=`
**replaces that whole set** rather than adding to it. No credentials — access is
the export ACL, which already lists exactly the three node IPs.

⚠️ Migrate, do not cut over. Point Longhorn at NFS, take one full backup of every
volume, restore one into a scratch namespace, *then* delete the LXC. Backups in
the old S3 store are not readable through the NFS target.

**Gate:** a volume backed up to the NFS target and restored from it with the
Garage LXC stopped.

# Week 2 — Backups a compromised host cannot destroy

**This is the most important week in the plan.** Everything else improves the
estate; this one changes what a bad day can cost.

## The finding

`restic-push-oracle.sh` runs on `pve-2` and does `backup`, then
`forget --prune`, then `check` — over SFTP, with a key that lives on `pve-2`.
The weekly Synology copy is also a **push** from `pve-2`.

So root on `pve-2` — ransomware, a bad command, a compromised container that
escapes — can delete the off-site copy *and* the NAS copy. Two of the three
copies are destroyable from the one machine most likely to be the problem. The
third is the local one on the same box.

That is not a 3-2-1 backup. It is one copy in three places.

## The fix, in four parts

**1. Append-only REST server on `vps01`.** Replace the SFTP target with
`restic/rest-server` running `--append-only --private-repos`. In append-only
mode a client may add data but may not delete or overwrite it. `pve-2` keeps
backing up and keeps being able to `check`; it can no longer `forget` or `prune`.

**2. Retention moves off `pve-2`.** This is the trade-off, and it is not
optional: with append-only the repository grows until something prunes it, and
that something must hold a credential `pve-2` does not have. Run the maintenance
job on `vps01` itself, on a schedule, with the full credential and the repo
password stored only there. The pruning host is a trusted host by definition —
that is the whole model.

**3. Synology pulls instead of receiving.** Flip `weekly-push-to-synology.sh`
around: the job starts on the Synology inside its wake window, over a
read-only forced-command SSH key into `pve-2`, followed by a Btrfs snapshot.
`pve-2` then holds no credential that reaches the NAS at all.

**4. The cold spare becomes a quarterly offline copy.** Power on the second
OptiPlex, take a restic copy, power it off. A copy that is disconnected from
mains on hardware already sitting in the house. This is the "1" in 3-2-1-1-0.

## Verification that is allowed to fail

`restic check` alone verifies metadata. It will pass over a repository whose
data blobs are corrupt.

| Add | Catches |
|---|---|
| `restic check --read-data-subset=5%` weekly | bit rot and truncation in the actual data |
| File-count comparison in `restic-restore-drill.sh` | a silently excluded directory — the exact failure that kept the Immich library out of DR for months |
| Explicit exclusions with the reason written beside each | `media/library`, TSDB over 30 d, caches, container images |

**Gate for the week:** from `pve-2`, `restic forget` against the Oracle repo
**fails**. A deliberately corrupted blob is caught by the weekly read-data check.
A deliberately excluded directory is caught by the file count. The Synology has a
snapshot taken by a job `pve-2` never triggered.

# Week 3 — Write amplification

One host. The other two were checked and are correct as they stand.

## `pve-1` — remove ZFS from under the VM

`nvme0n1` holds the ZFS pool `cluster-storage`: single disk, no redundancy, and
its only contents are VM 810's disk — etcd plus one Longhorn replica. Proxmox
itself is on `nvme1n1`. **This is not a reinstall.** It is destroying a pool
that holds one rebuildable thing.

Measured here: 0.365 MB/s written inside the VM, 1.29 MB/s written to the NVMe.
**3.5x**, from a 16K `volblocksize` under 4K guest writes, on QLC at 34% wear
with roughly 3.2 years left.

```
kubectl drain kubernetes-1 --ignore-daemonsets --delete-emptydir-data
talosctl -n kubernetes-1 shutdown
qm destroy 810
zpool destroy cluster-storage
pvcreate /dev/nvme0n1 && vgcreate vg-cluster /dev/nvme0n1
lvcreate -l 100%FREE -T vg-cluster/cluster-thin
pvesm add lvmthin cluster-storage --vgname vg-cluster --thinpool cluster-thin
cd talos/terraform && terraform apply      # same MAC, same IP
task talos:apply                            # then per docs/dr-quickstart.md
```

The Longhorn replica rebuilds from `kubernetes-2` and `kubernetes-3` — about
35 GB at `concurrentReplicaRebuildPerNodeLimit: 1` over 1 GbE shared with etcd.
Quorum holds on the other two nodes throughout. Hardware transcoding is down for
the duration; nothing else is.

**Expected:** ~112 GB/day → ~40 GB/day physical. Endurance ~3.2 → ~9 years.
This is the NVMe purchase the plan cancels.

⚠️ `talos/THREE-NODE.md:110` measures on `nvme1n1` while
`proxmox/pve-1/README.md` says `cluster-storage` is `nvme0n1`. One of them is
wrong. Confirm on the host before touching anything, and fix the doc.

**Gate:** `lvs` shows the thin pool, node `Ready`, all replicas `Healthy`, and
`/proc/diskstats` on the **host** confirms the new rate over 24 h. Never measure
this in the guest — that error once put the disk's life at "fourteen years".

## `pve-2` — nothing, and here is why that changed

An earlier draft said to rebuild VM 811's disk at `volblocksize=4K`. Research
contradicted it, so it is out.

The reasoning was that a 16K block under 4K writes forces read-modify-write, so
a 4K block removes it. True as far as it goes. What it ignored is what a 4K
block costs: a block pointer and checksum per 4 KB instead of per 16 KB,
metadata written with `copies=2`, and compression that cannot work at all
because there is nothing smaller than a sector to compress into. Proxmox forum
measurements of the full stack put 4K writes *worse* than 16K, not better.

So the sign of the change is unknown without measuring, and the payoff is small:
both `rpool` members are Intel D3-S4510s at **0% wear after 9,000+ hours**.
Amplification here costs IOPS and etcd fsync latency, not disk life.

This is the trap `talos/THREE-NODE.md` already documented — amplification is not
a constant, and pricing a change by theory rather than measurement is what
produced the wrong estimate last time.

**Decision: change nothing.** If it is ever revisited, the experiment is a clone
of VM 811 on an 8K zvol, both running 24 h, compared at `/proc/diskstats`.

⚠️ A raw file on a ZFS dataset is not an alternative either. A 4K overwrite
inside a 64K record is a 64K read-modify-write — 16x, worse than the zvol's 4x.
Block size is the variable; zvol-versus-file is not.

## `pve-3` — nothing

The D3-S4510 is passed raw into VM 812. Already correct, and it is the only disk
in the fleet with power-loss protection, which is what makes it the right home
for etcd.

# Week 4 — Segmentation, with the switch you have

Both open criticals in `SECURITY-AUDIT.md` can be closed now. Neither needs the
managed switch they were being held for.

## Day 1 — C2: OPT1 cannot reach the LAN

The current block rules cover `proto tcp` and `proto icmp` only, and nine per-IP
passes reach `<LAN__NETWORK>` — among them the TV and a tablet. From
`10.57.97.106` the audit reached Proxmox 8006, iDRAC 443 and 5900, NFS 2049,
etcd 2379 and kubelet 10250.

1. Delete or narrow the catch-all `1666203519` to `OPT1 → !LAN`.
2. Replace the per-protocol blocks with a block on **any** protocol,
   `OPT1 → LAN`, placed before every pass rule.
3. Narrow `any → 10.57.57.1` to port 53.
4. Rewrite the nine per-IP passes as single-service passes — the TV to
   Jellyfin `10.57.57.107:8096`, nothing else.

Highest value item in the whole document for the time it takes.

## Day 2 — C1: the BMC leaves the LAN

This was waiting for VLANs on a managed switch. It does not have to: `igb3`
carries no traffic and holds only a stale any-any rule.

Run a cable from `igb3` directly into the iDRAC port. Give it `10.57.10.0/30` as
OPT2. The BMC is then on a segment with exactly one other device, reachable only
through the tailnet, with no switch involved. While there: disable password
authentication on the iDRAC SSH, disable TLS 1.1, and update the iDRAC8
firmware — the current one predates the Terrapin countermeasure.

## Day 3 — The hypervisor firewall

Proxmox's firewall is off entirely, so anything on the LAN reaches 8006.

Do it in the documented order, because the failure mode is locking yourself out:
create a `management` IPSet at datacenter level holding the tailnet
(`100.64.0.0/10`) and the workstation, add the ACCEPT rules for 8006 and 22
against that IPSet **first**, verify from both a tailnet address and the
workstation, and only then set the default input policy to DROP. Datacenter
rules are evaluated before node rules, so the baseline goes there once and
applies to all three hosts.

## Day 4 — The cheap remainder

pfSense SSH password authentication off, the two-year-expired GUI certificate
regenerated, the stale any-any rules on `igb3` and `bridge0` deleted, the stale
WAN rule to `.60` deleted, Hue Bridge moved to OPT1, NAT-PMP disabled unless
something explicitly needs it.

## Day 5 — `no_root_squash`, one export at a time

Every export still carries `no_root_squash`, so a permitted client can act as
root on the exported tree. Red Hat's guidance is unambiguous about not using it,
and the ACLs being per-host is mitigation, not a fix.

It is not a drop-in change: kubelet applies `fsGroup` to in-tree NFS volumes and
the ARR pods use `fsGroupChangePolicy: OnRootMismatch`, so a squashed chown can
stop pods starting. Do `media/backups` first — no pod mounts it with `fsGroup`
— then `public/library`, then `media/library` last, each with a rollback and a
pod restart to prove it.

**Gate for the week:** from an OPT1 host, Proxmox, iDRAC, NFS, etcd and kubelet
are all unreachable. iDRAC is unreachable from the LAN and reachable from the
tailnet. 8006 is unreachable from a LAN address that is not in the IPSet.

# Week 5 — Least privilege inside the cluster

## Kubernetes audit logging

There is currently no record of what touched the API. On Talos this cannot be a
file you edit on the host — the policy goes in the machine config, under
`cluster.apiServer.extraArgs` (`audit-log-path`, `audit-log-maxage`,
`audit-log-maxbackup`, `audit-log-maxsize`, `audit-policy-file`) with the policy
file itself supplied through `cluster.apiServer.extraVolumes` and
`machine.files`.

Policy: `Metadata` for most resources, `RequestResponse` for `secrets`,
`configmaps` and everything in `rbac.authorization.k8s.io`, `None` for the
read-only noise that would otherwise be 90% of the volume. Promtail tails the
log path into Loki, so it lands beside every other log.

## Headlamp stops being cluster-admin

Today access is a bearer token for a `cluster-admin` ServiceAccount minted with
`--duration=8760h` — a year-long, fully privileged credential, and the runbook
tells you to create it that way.

Default it to the built-in `view` ClusterRole, keep a separate `headlamp-admin`
binding you assume deliberately when you need it, and drop the token duration to
8 hours. The dashboard stays; the standing year-long root does not.

## A cluster-wide default deny

`default-deny-lateral` covers the `default` namespace only. A namespace-scoped
policy cannot express a baseline across all namespaces or control traffic to the
nodes; `CiliumClusterwideNetworkPolicy` is the resource that can, and it is the
right place for a security baseline while per-app rules stay next to their apps.

Add a cluster-wide default-deny-ingress baseline covering `observability`,
`storage`, `network` and `kube-system`, then the explicit allows each one needs.
Roll it out with `hubble observe --verdict DROPPED` open — that is how the
Jellyfin `ingress` entity omission was caught last time.

## Cilium host firewall — audit mode only

Cilium can extend the same policy model to the host namespace via
`hostFirewall.enabled` and a `nodeSelector` policy. It is the natural next step
and it is also how you lose a cluster: if the rules are defined in-cluster and
they lock you out, the way back in is the thing you locked.

So: **enable it in audit mode, and stop there for this plan.** Watch for a month.
Enforcement is a decision for October with a month of evidence behind it, not a
task for this week.

**Gate:** an audit entry appears in Loki for a secret read. Headlamp with the
default token can list pods and cannot delete one. A pod in `observability`
cannot open a connection to a pod in `default`.

# Week 6 — Lifecycle, and proving it all works

## A patch cadence that is written down

Unpatched is the normal state of a homelab because nothing says when. This table
is the whole mechanism:

| Layer | Cadence | How |
|---|---|---|
| Container images | continuous | Renovate PRs, already running |
| Talos OS | monthly | `talosctl upgrade`, one node at a time, `--preserve` |
| Kubernetes | quarterly | `talosctl upgrade-k8s`, staying within one minor of stable, never skipping a minor |
| Proxmox hosts | monthly | `apt dist-upgrade` + reboot, one host at a time |
| pfSense | on release | console access ready before starting |
| iDRAC / BIOS firmware | twice a year | and once immediately — Week 4 Day 2 |

Talos and Kubernetes upgrade independently and have a compatibility matrix;
`upgrade-k8s` carries its own safety checks. Snapshot each VM before its node's
turn — which is exactly what the Proxmox layer is kept for.

## Disks tell you before they fail

SMART is read today but no self-test is ever run, and a scrub that is *cancelled*
alerts nothing.

| Job | Cadence | Note |
|---|---|---|
| SMART short test | daily | all disks, off-peak |
| SMART long test | monthly | **staggered against the scrub — never overlapping** |
| ZFS scrub | monthly | datacenter-class SAS; monthly is the right interval for these, not weekly |
| Scrub *completion* check | in `nightly-checks.sh` | alert on "did not finish", not only on "errors found" |

## Longhorn's own gaps

| Add | Why |
|---|---|
| A `snapshot` recurring job beside the existing `backup` job | snapshots are the fast local recovery path; today there is only the nightly backup, so the RPO for a bad `kubectl delete` is 24 h |
| A `system-backup` recurring job | backs up Longhorn's own settings, volume metadata and recurring jobs — without it a rebuilt cluster is reconfigured by hand |
| A coverage check that fails when a PVC is in no group | backups are opt-in by PVC label today. A new app is silently unprotected until someone notices — the same class of failure that hid the Immich library |

## The three monitoring gaps

| Gap | Fix |
|---|---|
| UPS state is a manual `upsc` read | `nut_exporter` on `pve-2` → Prometheus. Without a series you learn the battery degraded at the moment you need it |
| Nothing watches the cluster from outside itself | Uptime Kuma on `vps01`, probing the internal gateway over the tailnet and the public edge directly. kube-state-metrics once went down with the host it was monitoring |
| No alert on the slow failures | scrub not completed, SMART reallocated sectors, NVMe wear over threshold, Longhorn free space under 20%, certificate under 14 days, restic snapshot older than 36 h |

## The drill

Quarterly, on the cold-spare OptiPlex, with the targets written before it starts:

| Scenario | RTO | RPO |
|---|---|---|
| One node lost, any of the three | ~8 min, automatic | 0 |
| Full cluster rebuild, different hardware | ≤ 90 min | 24 h |
| `vps01` rebuild (Hetzner fallback) | ≤ 20 min | 24 h |
| Total loss of `pve-2` | ≤ 4 h for data | 24 h — media accepted as lost |
| pfSense lost | ≤ 30 min | 0 — USB installer + config XML in two places |
| Switch lost | ~15 min, degraded | 0 — hosts move onto pfSense's own ports |

⚠️ The DR guard that requires three nodes blocks recovery when you are starting
from one. Fix or document the override before the drill, not during it.

**Gate:** a cluster restored on the spare in under 90 minutes with
`task dr:verify` green, and the file-count comparison passing.

## What this plan deliberately does not do

**Reinstall `pve-2` on ext4 + LVM-thin.** It buys one thing — removing a zvol
from under VM 811 — on disks at 0% wear after 9,000 hours, at the cost of
rebuilding the backup hub, the NFS server and the Nextcloud VM. And there is no
cheap online substitute either, per Week 3. Largest-looking item in the
greenfield design, worst ratio in it.

**Consolidate the 12 SAS disks into one wide vdev.** `media` is 2 x raidz2-6.
One 12-wide raidz2 would take usable capacity from 4.8 TB to 6 TB, about +25%.
Three reasons not to:

- *Capacity is not the constraint.* The library is ~1.1 TB against ~4.3 TiB
  usable — roughly a quarter full.
- *It is strictly less survivable.* Two vdevs lose the pool only if three
  failures land in the same vdev: 40 of the 220 ways three disks out of twelve
  can fail, so **82% of three-disk failures survive**. A 12-wide raidz2 dies at
  the third failure, every time. ZFS also skips healthy vdevs when resilvering,
  so a rebuild reads six disks instead of twelve. General guidance puts a raidz
  group at 3-9 disks, with 6 the standard raidz2 width.
- *There is no safe migration.* A raidz vdev cannot be removed, so this means
  destroy and recreate — moving ~1.1 TB of media that by this repo's own
  accounting has no second copy anywhere. Risking the only copy of the library
  for capacity that is not needed is the worst trade available.

The current layout also grows six disks at a time instead of twelve, which is
the only realistic way it ever gets upgraded.

**Remove Nextcloud.** Live since 2026-08-20, and it is what replaced Filebrowser
and the Synology home shares. Syncthing plus Radicale does not cover its sharing
or web access; swapping them is simplification theatre paid for with three weeks
of migration work.

**Merge the two Jellyfin instances.** They look like duplication and are not.
The public one carries a curated 1080p library on SSD so streaming to friends
never wakes the SAS array, holds two shared accounts rather than yours, and is
the only internet-facing surface of the two. Merging would put the personal 4K
library behind the process that faces the internet.

**Enforce the Cilium host firewall.** Audit mode this quarter. Enforcement is a
decision to make with a month of evidence, not a task to schedule blind.

**Retire the R730xd.** ~110 W of the estate's ~165 W and the single largest
efficiency item that exists — blocked on where 3.6 TB of array storage would
otherwise live. That is a purchase. Deliberated and postponed on 2026-08-27;
nothing here changes that.
